Decision Register

Architectural and product decisions made so far, with rationale. Update when a pending decision is resolved.

Map Renderer: MapLibre GL JS (not Leaflet) 2026-05-11
Decision: Use MapLibre GL JS for the frontend map.
Rationale: WebGL-based rendering handles 100+ animated markers + 3,700 stop dots + 50 route polylines without frame drops. Leaflet uses SVG by default and would degrade under full-system load. MapLibre is free, open-source, and requires no API key (unlike Mapbox).
Tradeoff: Slightly steeper learning curve than react-leaflet; bundle size is larger (~300KB vs ~40KB). Worth it for performance headroom.
Backend Language: Python / FastAPI 2026-05-11
Decision: Use Python + FastAPI for the backend proxy.
Rationale: The gtfs-realtime-bindings Python library is official and well-maintained. Python also has the best GTFS static processing ecosystem (partridge, gtfs-kit). FastAPI gives async polling, auto-generated OpenAPI docs, and a fast development loop.
Tradeoff: Node.js would unify the language stack (if frontend is React). Accept the split — the backend is thin enough that language switching cost is low.
Backend Caches Last Feed Response 2026-05-11
Decision: The backend polls Metro's feed on its own 30-second timer and caches the parsed result. All client requests receive the cached JSON — the backend never fetches from Metro per-client-request.
Rationale: Prevents hammering the Metro feed under multi-user load. Keeps server-side polling rate constant regardless of client count. A naive per-request fetch could trigger rate limiting or IP blocking.
Headsign Join Strategy: Static Lookup at Startup 2026-05-11
Decision: On backend startup, load trips.txt from the static GTFS feed into a trip_id → headsign dict in memory. RT vehicle positions carry only trip_id; the backend enriches each vehicle with the headsign from this dict before serving JSON to clients.
Rationale: RT feed does not include headsigns in vehicle positions. This is the standard GTFS-RT integration pattern. The dict is small (6,435 entries).
Note: Dict must be refreshed when the static feed is updated (quarterly).
Route Colors: From GTFS route_color (no manual assignment) 2026-05-11
Decision: Use the route_color hex values from routes.txt directly. All 50 routes have values — no manual color table needed.
Note: Verify colors are visually distinct when multiple routes overlap on the map. If two routes share a similar color, consider a manual override table for just those routes.
Map Tiles: OpenStreetMap Raster (inline style, no API key) 2026-05-11
Decision: Use an inline MapLibre style object pointing at tile.openstreetmap.org raster tiles. No external style URL, no API key.
Rationale: MapLibre's demo style (demotiles.maplibre.org) renders as a plain green world outline — not useful. OSM tiles are free for reasonable/non-commercial use, universally available, and show real streets immediately without registration.
Note for production: OSM's tile usage policy discourages heavy production traffic directly on their servers. Before launch, switch to a CDN-backed tile provider (MapTiler free tier, Stadia Maps, or self-host with Protomaps). No code changes needed — just swap the tile URL in Map.tsx.
Direction Filter: Headsign Keyword ("downtown") 2026-05-11
Decision: Classify inbound=True when "downtown" in headsign.lower(); False when headsign exists but lacks "downtown" (outbound + cross-town routes); None when headsign is unknown.
Rationale: Scanned all 6,435 trips — 36/50 routes have clean inbound/outbound signals. 14 cross-town routes (5, 12, 22, 24, 31, 36, 37, 38, 41, 51, 61, 65, 67, 100) have no downtown destination and correctly fall into the "Outbound" bucket. The 410 dash-format headsigns (e.g. "Montgomery Rd- Downtown via Walnut Hills") are also covered since "downtown" appears in the string.
Filter logic: Inbound → inbound===true; Outbound → inbound===false || null; All → everything.

Maintenance Guide

This app requires periodic manual maintenance. These tasks are non-negotiable — skipping them causes silent inaccuracies.

Quarterly (every GTFS feed update)

  1. Download new GTFS static zip from go-metro.com/uploads/GTFS/google_transit_info.zip
  2. Check feed_info.txt for new active period dates
  3. Run python validate_feed.py --static — verify route_color and trip_headsign still present
  4. Diff routes.txt against previous version — identify added/discontinued routes
  5. Update config/route_categories.json for any route changes (new routes default to "Minor" pending classification)
  6. Re-run GTFS → GeoJSON processor script to update route lines and stops
  7. If trip variant labels break (4-A, 43-S, etc.), update config/trip_variants.json and test regex against new headsigns
  8. Restart backend so it loads the new static data
  9. Verify map renders correctly with new data — spot-check 3–4 routes visually

After Metro Service Changes (mid-quarter)

  1. Monitor Metro's alerts feed and social media for service restructuring announcements
  2. If a route changes its path, the shape in GTFS will update — re-process GeoJSON
  3. If a route is discontinued, remove from category config to avoid empty dropdowns

Ongoing Monitoring

  • Watch /api/health — consecutive failure count should stay at 0
  • If failures spike: check tmgtfsprd.sorttrpcloud.com is still reachable
  • If feed disappears entirely: Metro may have changed the URL — check go-metro.com/developers for updates
Next Mandatory Maintenance Window

GTFS static feed expires May 30, 2026. Re-run validation and update processed static files before or immediately after the new feed is published (~June 1, 2026). The backend will continue serving vehicles from the RT feed even after static data expires, but headsigns and route geometry will be stale.
