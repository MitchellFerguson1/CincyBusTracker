CincyBusTrackr

Real-Time Cincinnati Metro Bus Tracker — Product Requirements Specification

Version: 1.0
Date: May 2026
Status: Draft

1. Executive Summary

CincyBusTrackr is a web application that provides real-time visualization of Cincinnati Metro (SORTA) bus positions across all fixed routes. It replaces the defunct Metro real-time tracking tool — removed from go-metro.com in late 2025, fully offline as of early 2026 — with a significantly enhanced multi-route "command center" view.

Core value proposition: A transit enthusiast and commuter tool that displays multiple routes simultaneously with directional context. The former Metro tracker was limited to 2 routes at a time, each showing only one direction. This project removes both constraints.

Inspiration: TrainTrackr.io — physical LED maps showing real-time train positions for Boston, NYC, Chicago, DC, and Bay Area transit systems. CincyBusTrackr is the software equivalent adapted for Cincinnati's bus network.

2. Problem Statement

Metro's official real-time tracker was removed without replacement. Its limitations were severe:

  • Maximum of 2 routes viewable simultaneously
  • Each route displayed only one direction (inbound OR outbound) per panel
  • No way to see both directions of a single route at once
  • Workaround required opening 15+ browser tabs across multiple monitors

Third-party apps (Transit App, Google Maps) show individual route arrivals but do not provide a system-wide real-time overview. No existing tool fills this gap.

3. Data Sources & Feasibility

3.1 GTFS Static Feed

Metro publishes a GTFS static feed containing all route definitions, stop locations, trip patterns, and schedules.

3.2 GTFS-Realtime Feed

Metro publishes a GTFS-RT protobuf feed providing live vehicle positions, trip updates, and service alerts.

Feed TypeEndpoint
Vehicle Positions + Trip Updatestmgtfsprd.sorttrpcloud.com/TMGTFSRealTimeWebService/gtfs-realtime/trapezerealtimefeed.pb
Service Alertstmgtfsprd.sorttrpcloud.com/TMGTFSRealTimeWebService/alert/alerts.pb
Critical Dependency

This entire project is viable only as long as Metro continues publishing the GTFS-RT feed. The feed URL and availability must be tested and monitored. If Metro restricts access or requires API keys in the future, the project would need to negotiate access. There is no technical workaround — no feed means no project.

3.3 Stop Data

All 3,700+ stops with unique IDs, lat/lon coordinates, and route associations are included in the GTFS static feed (stops.txt). The partially-collected manual stop dataset is unnecessary unless it contains enrichment data not in the GTFS feed (informal stop names, accessibility notes, etc.). Verify before duplicating effort.

5. Functional Requirements

5.1 Route Selection Panel

The route selector is the primary control surface. It uses a two-axis selection model: direction × route category.

5.1.1 Direction Selector (Row 1)

Three mutually-exclusive toggle buttons:

"All" is the default state. When active, the bus icon's directional indicator (see 5.3) becomes essential for distinguishing direction of travel.

Category buttons, each functioning as a dropdown with multi-select:

Data Mapping Required

The GTFS routes.txt does not include a "category" field (Core/Major/Minor/etc.). This classification must be maintained as a separate lookup table within the application, manually mapped from Metro's published route classifications. This table needs updating when Metro changes service (at least quarterly).

5.2 Map Display

The primary display is an interactive map showing:

  • Route lines: Rendered from GTFS shapes.txt polylines, color-coded per route
  • Stop markers: Small dots at each stop along selected routes
  • Bus icons: Positioned at real-time GPS coordinates from the GTFS-RT feed
  • Pan/zoom: Standard map interaction; defaults to full Metro service area
Performance Concern

When "All" routes are selected: ~50 routes, 3,700+ stops, and potentially 100+ active buses must render simultaneously without frame drops. Mitigations: cluster stops at low zoom levels, simplify route polylines, use canvas rendering over SVG for markers, lazy-load off-screen route geometry.

5.3 Bus Icon Design

The bus icon is a directional pentagon: a rectangle with one end tapering to a triangular point indicating direction of travel.

Shape Specification

  • Base shape: Rectangle ~40×20px (scalable)
  • Directional indicator: One short side extends to a triangular point
  • Orientation: Pointed end faces direction of travel (from GTFS-RT bearing field)
  • Interior text: Route number (and variant suffix if applicable)
  • Background color: Route's assigned color
  • Text color: White or dark, auto-selected for contrast

5.3.1 Special Trip Labeling

Some routes have variant trips (school specials, branch terminations) that need visual distinction. The icon interior uses a route-suffix notation:

LabelMeaningExample
4-ARoute 4 Amberly specialAfternoon school trip via Amberly
4-EARoute 4 Evanston AcademyAfternoon school trip to Evanston Academy
43-ERoute 43 Evendale branchTerminates at Evendale
43-SRoute 43 Sharonville branchTerminates at Sharonville
43-RRoute 43 Roselawn specialSpecial Roselawn routing
41-A / 41-AHSRoute 41 Aiken HS tripSuffix abbreviates destination (not standardized)
Data Mapping Required

The suffix labels are not standard GTFS fields. They must be derived from either: (a) pattern-matching on trip_headsign, (b) a manually maintained lookup table mapping trip_id patterns to suffix labels, or (c) stop-sequence analysis detecting terminal stop deviations. Option (b) is most reliable but requires quarterly maintenance. This is the single most maintenance-intensive part of the application.

5.4 Real-Time Data Refresh

The application polls the GTFS-RT feed at a configurable interval. Recommended default: 15–30 seconds.

  • Backend parses protobuf using gtfs-realtime-bindings library
  • Vehicle positions include: lat, lon, bearing/heading, speed, trip_id, vehicle_id, timestamp
  • Stale data (timestamp > 5 min old) should be visually dimmed or hidden
  • Smooth animation between poll intervals (interpolate position along route shape) is Phase 2

5.5 Information Panel Phase 2

Clicking a bus icon displays a popover with:

  • Route number and headsign (destination)
  • Current speed
  • Next stop and estimated arrival
  • Trip variant label (if applicable)
  • Last position update timestamp

Vehicle ID (bus number) is available in the feed but explicitly deprioritized.

7.2 Data Flow

  1. Backend polls Metro GTFS-RT feed every 15–30 seconds
  2. Backend parses protobuf, extracts vehicle positions, matches to routes/trips via GTFS static data
  3. Backend serves parsed positions as JSON via REST endpoint (or WebSocket for push)
  4. Frontend fetches positions, matches to route shapes, renders bus icons on map
  5. GTFS static data (route geometry, stops) is preprocessed into static JSON, cached client-side
Why a backend proxy?

Parsing protobuf directly in the browser is possible but adds bundle size and exposes the feed URL. A thin backend also enables route category mapping, trip variant labels, data enrichment, and CORS handling — all server-side.

8. Route Classification Reference

Metro classifies routes into service tiers. This mapping must be maintained as a configuration file (not hardcoded) and validated against Metro's current published schedules quarterly.

CategoryCharacteristicsMaintenance Trigger
CoreHighest frequency, 7-day service, primary corridorsRarely changes
MajorModerate frequency, broad coverageQuarterly review
MinorLower frequency or limited spanQuarterly review
CommuterPeak-direction, peak-period onlySeasonal schedule changes
ExpressLimited-stop, longer distanceSeasonal schedule changes

Source for initial mapping: Metro's published schedule booklet and the route listings on go-metro.com/riding-metro/fixed-route-schedules/. The GTFS feed does not include this classification.

9. Trip Variant Labeling Logic

The suffix-based trip labeling system (e.g., 4-A, 43-S) requires a mapping between GTFS trip patterns and display labels. This is the most maintenance-intensive component.

9.1 Approach Comparison

ApproachProsCons
Manual lookup table
(trip_id pattern → suffix)		 Most accurate, full control Requires update every schedule change; brittle if trip_id format changes
Headsign parsing
(regex on trip_headsign)		 Adapts automatically to new GTFS data Headsign text may be inconsistent; may miss edge cases
Stop-sequence analysis
(detect branch by terminal stop)		 Structural, not text-dependent Complex to implement; can't distinguish school specials from regular branches
Recommendation

Start with a manual lookup table for MVP. The variant trips are a known, finite set. Invest in automated detection only if quarterly maintenance becomes unsustainable. Consider a hybrid: use headsign parsing as the default, with manual overrides for known edge cases.

10. Phasing

Phase 1 — MVP MVP

  • Map display with route lines and bus position icons
  • Direction selector (Inbound / Outbound / All)
  • Route category selector with multi-select dropdowns
  • Directional pentagon bus icons with route number
  • 15–30 second auto-refresh of bus positions
  • Stale data indicator (dim buses with old timestamps)
  • Stop dots along route lines
  • Mobile-responsive layout (desktop-primary)

Phase 2 — Enhancements Phase 2

  • Click-to-inspect bus popover (headsign, speed, next stop, ETA)
  • Trip variant suffix labels (4-A, 43-S, etc.)
  • Smooth position animation between poll intervals
  • Service alerts overlay (from GTFS-RT alerts feed)
  • URL-based state sharing (?routes=4,43&dir=all)
  • Dark mode

Phase 3 — Aspirational Phase 3

  • Historical playback (record positions, replay a day's service)
  • On-time performance heatmap by route segment
  • User-defined route groups ("my commute" presets)
  • Push notifications for specific arrivals (requires accounts)
  • PWA support for home-screen install

12. Open Questions for Resolution

These must be answered before development begins. Items marked blocking prevent any work from starting.

  1. BLOCKING: Is the GTFS-RT feed currently accessible without an API key or authentication? Hit the endpoint and confirm a valid protobuf response.
  2. BLOCKING: Does the GTFS-RT feed include vehicle bearing/heading? Required for directional icon rotation. If absent, direction must be inferred from sequential position deltas.
  3. What is the actual update frequency of the GTFS-RT feed? (Determines minimum useful poll interval.)
  4. Does Metro's GTFS data include route_color values, or must colors be assigned manually?
  5. How are school special trips represented in the GTFS data? (Separate trip_ids? Different service_id? Different trip_headsign?)
  6. Is there a rate limit or usage policy on the GTFS-RT endpoint? Metro's developer page doesn't specify one, but aggressive polling could trigger blocking.
  7. What is the project name? "CincyBusTrackr" is a placeholder — needs to be finalized before any public-facing work.
  8. Domain and hosting budget? Even minimal hosting (Fly.io, Render) has a cost floor for the always-on backend proxy.
Recommended First Step

Before any design or development work: write a 20-line Python script that fetches the GTFS-RT feed, parses it, and prints vehicle positions. This validates the entire data pipeline in under an hour and answers questions 1, 2, 3, and partially 5 above. If this script fails, the project needs a different data strategy.
